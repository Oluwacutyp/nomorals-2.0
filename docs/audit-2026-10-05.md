## 1. LLM Providers and Routing

### What it is
Capability-based model selection (`broker.py`) sitting above a health-tracking failover router (`router.py`), with 8 provider implementations (Groq, HF serverless, OpenRouter, Ollama, llama.cpp, OpenAI-compat, mock, OCR).

### Implementation level
**Excellent.** This is some of the best-engineered code in the repo:
- `ModelBroker` scores cards by capability match → operator override → benchmark score → trajectory success → latency rank → specialization → local preference
- `LLMRouter` tracks per-provider health (calls, failures, error rate, latency, cooldowns), fails over automatically, supports hot-swap
- Rate limits (429) get 2-minute cooldown vs 30s for other errors
- Repair hooks for self-healing providers

### How it actually works
`router.chat()` → tries active provider → on failure, marks unhealthy, tries next in chain → typed `ModelError` if chain exhausted. Broker optionally consults before each call to pick the best card for the capability.

### How it's supposed to work
Seamless failover across free/local/cloud providers. Local-first when available. Never brain-dead.

### What's broken
**Everything operational.** The code is perfect; the configuration is broken:
- Groq: rate-limited (or wrong model name `llama-3.3-70b-versatile`)
- HF serverless: model not hosted (`Phi-3.5-mini-instruct` not on new router)
- OpenRouter: model name not hosted (`openrouter/free` isn't a real model)
- No local model running (waiting on 3.8B training)
- Result: **Devon currently has no working brain.** All the beautiful routing code is routing to dead ends.

### What could be better
1. **Validate model names at startup.** The router should probe each provider with a cheap call on boot and mark invalid-model providers as unhealthy immediately, instead of discovering it at chat time.
2. **Ship with known-good free model names.** The defaults should be verified against actual provider catalogs, not guessed.
3. **Local model auto-download.** If no cloud provider works and no local model exists, offer to download a small GGUF automatically.

## 2. Memory System

### What it is
`MemoryManager` with dual-index recall (vector + FTS), decay, consolidation, and origin-boosted ranking.

### Implementation level
**Good, with one critical weakness.** The recall algorithm is sophisticated:
- Semantic pass (vector search, over-fetch 6x)
- Lexical pass (FTS, catches identifiers vectors blur)
- Merged scoring with recency decay, importance weighting, origin boost
- Tag filtering, private-record exclusion, TTL support

### How it actually works
`brain.py` calls `responder.recall(text, limit=5, origin=...)` → `memory.recall()` → returns records with `score > 0.05` → injected into prompt context.

### How it's supposed to work
"Recall what we discussed about X" should surface relevant past conversations semantically.

### What's broken/weak
1. **Embedder defaults to feature-hashing, not real embeddings.** The `Embedder` class uses a "hashing" provider by default — it's a bag-of-words hash with stemming, not semantic. The docstring is honest ("degrades only on paraphrase") but this means "semantic" recall is really just fancy keyword matching. Without an embedding provider configured, Devon can't understand paraphrases or conceptual similarity.
2. **Recall threshold of 0.05 is basically "everything."** This low bar means noise gets into the prompt. The scoring is good but the filter is too permissive.
3. **Consolidation trigger is crude.** `consolidate()` runs when memory count hits 5000, but there's no evidence it's effective at distilling vs just summarizing.

### What could be better
1. **Configure a real embedding provider.** Even a small local model (e.g., `all-MiniLM-L6-v2` via ONNX) would massively improve recall quality.
2. **Raise the recall threshold** or make it adaptive based on score distribution.
3. **Session-filtered recall.** The `origin` boost exists but isn't a filter. Add an option to recall only from the current session/conversation.

## 3. Proactive / Autonomy

### What it is
`AutonomyAgent`: heartbeat-driven (default 15 min) proactive messaging with mood, quiet hours, per-day caps, and an approval flow.

### Implementation level
**Well-designed, neutered by default.** The code is thoughtful:
- Three modes: `off`, `suggest` (default), `auto`
- Quiet hours (22:00–08:00), max 6 DMs/day, 2 group posts/day
- Group posts never mention the partner or that she's AI
- All actions journaled in `proactive_log`

### How it actually works
Heartbeat fires → checks mood/time/silence duration → generates message via LLM → in `suggest` mode, writes to `proactive_log` as pending → owner must approve via `nm partner --approve <id>`.

### How it's supposed to work
"She initiates, on her own clock." A partner who checks in, not a tool that waits.

### What's broken/weak
1. **Default mode is `suggest`, which means nothing ever sends.** The user has to manually approve every proactive message. This defeats the purpose. It's "safe" but it's not autonomous.
2. **Requires a working LLM to generate messages.** With no brain (see §1), proactive is completely dead. Even in `auto` mode, it would silently fail.
3. **No proactive *actions*, only messages.** It can send a check-in text, but can't proactively do things like "I noticed X, so I did Y."

### What could be better
1. **Default to `auto` for the owner.** The user explicitly wants unlimited power mode. `suggest` should be opt-in, not default.
2. **Proactive tool use.** Let the autonomy agent run tools (check calendar, search, etc.) and report findings, not just send canned check-ins.
3. **Smarter triggers.** Currently time-based. Should also trigger on events (new email, price alert, etc.).

## 4. Telegram Connectors

### What it is
Dual-endpoint Telegram: userbot (Telethon, full owner powers) + BotFather bot (public, gated to chat/games).

### Implementation level
**Functional but fragile.** 1,327 lines in `telegram.py`. The entity resolution logic has been the source of repeated bugs:
- Group→DM redirect (fixed 3 times: `08e73bc`, `6a320d3`, `de6c7f2`, `88d6741`)
- Self-reply loops (fixed with bot-flag check + token ID comparison)
- Typing indicator spam (fixed with decide-before-typing)

### How it actually works
`_handle_inbound` → resolve entity via `event.chat` → `input_chat` → `input_sender` (DM only) → `client.get_entity` → synthetic fallback → build `ChatMessage` → gateway dispatch.

### How it's supposed to work
Messages arrive, get correctly attributed to their chat (group vs DM), replies go back to the right place.

### What's broken/weak
1. **Entity resolution is a house of cards.** Every fix has been "don't use X when it's a group." The fundamental problem is Telethon's event objects are ambiguous, and the code has 5+ fallback layers. It works now but it's fragile.
2. **No integration test with real Telethon events.** All tests use mocks. The bugs only manifest with real event objects.
3. **BotFather bot gating is new and unverified.** The "public chat+games only" gate (`0cd0374`) hasn't been phone-tested.

### What could be better
1. **Simplify entity resolution.** Instead of 5 fallbacks, determine chat type from `event.chat_id` sign first, then use exactly one resolution path per type.
2. **Log the full event object on failures.** When entity resolution fails, dump the event for post-mortem instead of guessing.

## 5. Game System

### What it is
Full RPG: players, XP/levels, gear, skills, combat, PvP, gifting, economy, achievements, arena, mastery.

### Implementation level
**Massive and feature-rich, identity was fundamentally broken.** 46 methods in `players.py` alone. Systems include:
- Performance-based economy (`coin_breakdown` with difficulty multipliers, streaks)
- 14 dual-cast skill combos
- Hunter ranks (E/D/C/B/A/S) for arena scaling
- Soft-delete with 48h restore
- Username-based identity resolution

### How it actually works (post-fix)
`PlayerStore.get(platform, sender_id, name, username)` → ID-keyed lookup → legacy name merge → username merge → create if new. Gifts resolve by username → display name → key.

### How it's supposed to work
One profile per human, stable across name changes, no duplicates across endpoints.

### What's broken/weak
1. **Identity system was built on names, not IDs.** This caused the entire Mary/Main merge disaster. Fixed now (migrations 77, 79, username merging) but the fix is reactive — the schema still has legacy name-keyed rows.
2. **No phone verification of the fixes.** The untangle (`cbaaa0b`), username merge (`b48949d`), and group fix (`88d6741`) are all pushed but not phone-confirmed.
3. **Economy balance is untested at scale.** The performance-based payouts are theoretically sound but no data on whether they break progression.

### What could be better
1. **Purge legacy name-keyed rows.** After a migration period, delete the old `telegram:Name` rows entirely. They're a liability.
2. **Add a `/game verify` command** that shows the player's canonical ID, username, and linked aliases for debugging.
3. **PvP matchmaking.** Currently manual. Could auto-match based on level.

## 6. Console / UI

### What it is
`nomorals/console/`: colored logging, live dashboard, console commands. Just overhauled (`ed93ffb`).

### Implementation level
**Good (new).** 
- ANSI colors (cyan/green/blue/yellow/magenta — red/black banned per user preference)
- `dashboard` command shows uptime, adapters, traffic, scheduler jobs, player count
- `jobs`, `status`, `clear`, `help` commands
- Command hook intercepts before brain (doesn't pollute chat)

### How it actually works
`LocalAdapter` has optional `command_hook`. `run_chat_bot.py` wires `ConsoleCommands` with a snapshot provider. Colors only when stderr is a TTY.

### What's weak
1. **Dashboard is snapshot, not live-updating.** You type `dashboard` and get a static view. No auto-refresh.
2. **No scrollback/search.** Console output is ephemeral.

### What could be better
1. **Auto-refreshing dashboard** (e.g., `dashboard --watch`).
2. **Log filtering** by module or level from the console.

## 7. Credential Vaults

### What it is
Two encrypted vaults:
- `nomorals/accounts/vault.py`: AES-256-CTR + HMAC, PBKDF2 key derivation, SQLite backend. General-purpose.
- `nomorals/agents/trial/vault.py`: scrypt + HMAC-SHA256, file-based. For single-account trials.

### Implementation level
**Good.** Real crypto, not theater. Per-credential keys, integrity validation, no plaintext storage.

### What's weak
1. **Two vaults is confusing.** Why not one? The trial vault seems redundant.
2. **No UI/API for management.** Credentials go in via code, not via chat command or dashboard.
3. **Master key storage.** The trial vault stores the key in `trial.key` next to the data (mode 0600). Honest docstring ("protects against casual eyeballs, not a stolen device") but weak.

### What could be better
1. **Unify into one vault.** Migrate trial vault into the accounts vault.
2. **Add `/vault store` / `/vault list` chat commands** for the owner.
3. **Hardware-backed key storage** on supported platforms.

## 8. Scheduler

### What it is
In-process cron: `at` / `every` / `daily` schedules, three payload types (message, tool, shell command), persisted in `schedule_jobs` table.

### Implementation level
**Solid.** Survives restarts, one-shot jobs auto-disable, tick loop on daemon thread, outcomes via Notifier.

### How it actually works
`Scheduler` starts with runtime → tick every 60s → check due jobs → execute payload → publish result via Notifier → update next run.

### What's weak
1. **In-process only.** If the bot isn't running, jobs don't fire. No system cron integration.
2. **No timezone support.** `daily 22:00` is in server local time. No per-job timezone.
3. **Shell command payload is a security risk.** Any job can run arbitrary shell commands. Should require explicit capability grant.

### What could be better
1. **Timezone-aware scheduling.**
2. **Job dependencies** (run B after A succeeds).
3. **Web UI for job management** (currently only via `/schedule` chat command and new `jobs` console command).

## Honest Overall Assessment

**What's genuinely good:**
- LLM routing architecture (broker + health tracking) is excellent
- Memory recall algorithm is sophisticated
- Game system is feature-rich and deep
- API server is complete with no stubs
- Scheduler is solid and persistent
- Credential encryption is real, not theater
- 342 test files shows serious testing investment

**What's genuinely bad:**
- The #1 feature (a working brain) doesn't work. Everything else is secondary.
- Too many systems are "built but not live-tested" (connectors, voice, proactive)
- Identity and entity resolution were built on shaky foundations and patched repeatedly
- The codebase is 30MB / 694 modules — impressive but also a maintenance burden. There's likely significant dead code.

**The one thing that matters most:**
Get a working LLM. Everything else — memory, proactive, personality, usefulness — depends on it. The 3.8B training is the highest-leverage work happening right now.
